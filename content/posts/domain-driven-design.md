세상에는 정말 많은 개발 이론이 있다. 기술 하나를 익혀 기능 하나 돌아가게 만드는 것도 벅찬데, TDD니 DDD니 이름이 비슷한 무언가가 계속 나온다.

이런 방법론이 괜히 생긴 것은 아니다. 개발은 혼자 하는 일이 아니고, 함께 일하는 사람이 많아질수록 같은 업무를 서로 다르게 이해한다. 오늘 알아볼 DDD도 이 차이를 줄이려는 고민에서 출발한다. 한국말로는 도메인 주도 설계다. 이름부터 벌써 묵직하다.

## 같은 주문 취소를 다르게 이해할 때

정의부터 외우기 전에 DDD가 필요한 상황부터 살펴보자. 주문팀, 결제팀, 물류팀과 고객센터가 따로 있는 쇼핑몰 회사를 가정해 보겠다.

어느 날 주문 취소 기능을 개선해 달라는 요청이 들어온다.

> **기획팀:** 배송 전에는 주문을 취소할 수 있게 해주세요.
>
> **주문팀:** 배송 전이 정확히 어느 상태까지인가요?
>
> **물류팀:** 송장이 발급되면 출고로 봅니다.
>
> **고객센터:** 송장이 나와도 실제 출고 전에는 취소해 주고 있는데요?
>
> **결제팀:** 주문 취소와 결제 환불은 다른 처리입니다.
>
> **개발자:** 정확한 기준은 어디에 정리되어 있나요?
>
> **기획팀:** 이전 담당자분이 잘 알고 계셨는데요.
>
> **개발자:** 그분은 퇴사하셨는데요.

잠시 정적이 흐른다.

그래도 일정은 잡혀 있다. 각 팀은 전달받은 내용을 바탕으로 기능을 만든다. 얼마 뒤 주문은 취소됐는데 환불이 되지 않고, 환불은 됐는데 쿠폰이 돌아오지 않는 일이 생긴다. 고객센터에서는 취소할 수 있다고 안내했지만 API에서는 거절하기도 한다.

코드보다 먼저 어긋난 것은 업무에 대한 이해였다. 같은 `주문 취소`를 주문팀은 상태 변경으로, 결제팀은 환불로, 물류팀은 출고 중단으로 받아들였다. 관련 규칙도 기획서와 코드, 오래된 대화와 담당자의 기억 속에 흩어져 있었다.

> 여러 사람이 복잡한 업무를 같은 말과 기준으로 이해하려면 어떻게 해야 할까?

DDD는 이 질문에서 출발한다.

## DDD는 업무를 코드의 중심에 놓는다

**도메인**은 소프트웨어로 해결하려는 현실의 문제 영역이다. 쇼핑몰이라면 상품을 판매하고 주문을 접수하며 결제와 배송을 처리하는 업무가 도메인에 해당한다. 데이터베이스나 메시지 큐는 이 업무를 구현하기 위해 선택하는 기술이다.

DDD는 기술보다 업무를 먼저 이해하고, 그 이해를 모델과 코드에 계속 반영하는 설계 방식이다. 이름에 등장하는 `Domain-Driven`도 도메인이 설계를 이끈다는 뜻이다.

처음 접하면 Entity, Aggregate와 Repository 같은 낯선 용어부터 눈에 들어온다. 하지만 패턴을 먼저 외우면 각각을 왜 사용하는지 놓치기 쉽다. 다음 순서로 보면 개념이 조금 더 자연스럽게 이어진다.

![업무 이해에서 경계와 모델을 거쳐 실행으로 이어지는 DDD 개념의 흐름](/images/posts/domain-driven-design/ddd-concept-map.svg "DDD를 따라가는 네 단계")

*DDD 개념을 처음 접할 때 따라가기 좋은 흐름*

먼저 사람들의 언어를 맞추고, 하나의 모델이 유효한 경계를 찾는다. 그다음 업무 규칙을 Entity, Value Object와 Aggregate로 표현하고, 애플리케이션이 이 모델을 사용하도록 연결한다.

이 글도 주문 취소 사례를 이 순서대로 따라간다.

## 같은 업무를 같은 말로 이해한다

주문 취소 기능을 제대로 만들려면 개발자는 먼저 업무 담당자에게 질문해야 한다.

- `배송 전`은 결제 완료 전인가, 송장 발급 전인가, 실제 출고 전인가?
- 주문 취소와 결제 환불은 동시에 끝나는가?
- 일부 상품만 취소할 수 있는가?
- 쿠폰과 재고는 어느 시점에 되돌리는가?

이 질문에 답하는 과정에서 주문팀은 `취소`, 결제팀은 `환불`, 물류팀은 `출고 중단`을 담당한다는 사실이 드러난다. 처음에는 하나처럼 보였던 기능이 실제로는 여러 업무의 협력으로 이루어져 있었다.

### 도메인 전문가는 업무의 예외를 알고 있다

실제 업무의 규칙과 예외를 잘 아는 사람을 **도메인 전문가**라고 부른다. 거창한 직책을 뜻하지는 않는다. 주문 상태를 관리하는 운영자, 환불 규정을 정하는 기획자와 반복되는 문의를 처리하는 고객센터 직원도 각자의 영역에서는 도메인 전문가다.

개발자는 이들과 함께 다음을 확인한다.

```text
고객이 주문 취소를 요청한다
→ 주문이 취소 가능한 상태인지 확인한다
→ 주문을 취소한다
→ 결제에 환불을 요청한다
→ 물류에 출고 중단을 요청한다
→ 쿠폰과 재고를 복구한다
```

단순한 순서처럼 보여도 각 단계에 질문이 생긴다. 환불 요청이 실패하면 주문 취소도 되돌려야 할까? 이미 출고됐다면 고객 반품으로 바뀌어야 할까? 이런 질문이 바로 코드에 남겨야 할 업무 지식이다.

### 대화에서 쓰는 말을 코드에서도 사용한다

함께 합의한 업무 언어를 **유비쿼터스 언어**라고 한다. 우리말로는 보편 언어라고도 부른다.

주문팀이 `취소`, 결제팀이 `환불`, 물류팀이 `출고 중단`이라고 구분하기로 했다면 문서와 화면뿐 아니라 코드에서도 같은 말을 사용한다.

```java
order.cancel();
refund.request();
shipment.stopDispatch();
```

반대로 코드에 `changeStatus(4)`만 남아 있다면 숫자 `4`가 어떤 업무 상태인지 다시 사람의 기억에 의존해야 한다. 유비쿼터스 언어는 용어집 하나를 만드는 데서 끝나지 않는다. 회의에서 사용한 말이 모델, 테스트와 코드에서도 같은 의미를 가져야 한다.

업무 흐름과 용어를 함께 찾을 때는 **이벤트 스토밍** 같은 방법을 활용할 수 있다. 업무에서 이미 일어난 사건을 시간 순서대로 펼쳐 놓고, 빠진 과정과 서로 다른 해석을 대화로 찾아가는 방식이다.

![EventStorming을 활용해 업무의 사건과 경계를 함께 탐색하는 모습](/images/posts/domain-driven-design/event-storming.jpg "EventStorming을 활용해 업무의 사건과 경계를 함께 탐색하는 모습")

*출처: [EventStorming 공식 사이트](https://www.eventstorming.com/)*

색상과 진행 방식보다 중요한 것은 각자 머릿속에 있던 업무를 한곳에 꺼내 놓는 일이다. 대화하면서 모델이 달라졌다면 실패한 것이 아니라, 구현 전에 오해를 발견한 것이다.

## 하나의 모델이 통하는 경계를 찾는다

업무 용어를 맞췄다고 회사 전체가 모든 단어를 하나의 뜻으로 사용해야 하는 것은 아니다. 같은 단어도 맡은 업무에 따라 필요한 의미가 달라진다.

상품팀의 `상품`에는 현재 판매 가격, 설명과 선택 가능한 옵션이 중요하다. 주문팀의 `상품`에는 고객이 주문한 당시의 이름, 가격과 수량이 중요하다. 상품팀이 오늘 가격을 바꿨다고 어제 결제한 주문 금액까지 바뀌어서는 안 된다.

DDD에서는 하나의 모델과 언어가 일관되게 통하는 범위를 **바운디드 컨텍스트**라고 한다. 우리말로 옮기면 `경계가 정해진 맥락` 정도다.

주문 취소도 경계에 따라 다른 책임을 가진다.

![주문·결제·배송 컨텍스트가 주문 취소를 서로 다른 책임으로 처리하는 모습](/images/posts/domain-driven-design/order-contexts.svg "주문 취소를 바라보는 세 바운디드 컨텍스트")

*주문 취소 사례를 세 바운디드 컨텍스트로 나눈 예*

주문 컨텍스트는 주문 상태를 바꾸고, 결제 컨텍스트는 환불 가능 여부와 금액을 판단하며, 배송 컨텍스트는 출고를 멈출 수 있는지 판단한다. 한 컨텍스트의 내부 객체를 다른 쪽에서 직접 고치는 대신 필요한 요청이나 사건을 주고받는다.

### 서브도메인과 바운디드 컨텍스트는 관점이 다르다

복잡한 도메인을 주문, 결제와 배송처럼 더 작은 업무 영역으로 나눈 것을 **서브도메인**이라고 한다. 바운디드 컨텍스트와 비슷해 보이지만 둘은 바라보는 대상이 다르다.

- **서브도메인:** 현실의 업무를 나눈 문제 영역
- **바운디드 컨텍스트:** 그 문제를 해결할 모델이 일관되게 통하는 경계

주문이라는 서브도메인을 하나의 주문 컨텍스트가 맡을 수도 있다. 시스템이 커지면 주문 접수와 주문 이력처럼 여러 컨텍스트가 나누어 맡을 수도 있다. 둘을 반드시 일대일로 맞추는 것이 목적은 아니다.

서브도메인은 회사에서 차지하는 중요도에 따라 핵심, 지원과 일반 서브도메인으로 구분하기도 한다.

| 구분 | 의미 | 쇼핑몰 예시 |
|---|---|---|
| 핵심 | 회사의 경쟁력을 만드는 업무 | 독자적인 추천·가격 정책 |
| 지원 | 핵심 업무를 돕는 회사 고유 업무 | 주문·정산 운영 |
| 일반 | 여러 회사가 비슷하게 해결하는 업무 | 이메일 발송 |

무엇이 핵심인지는 기술 난이도가 아니라 회사가 무엇으로 경쟁하는지에 따라 달라진다. 이 구분은 모든 영역에 같은 비용을 쓰지 않고 어디를 깊이 모델링할지 판단하는 데 도움을 준다.

## 도메인 모델은 업무 규칙을 코드에 남긴다

도메인과 경계를 찾았다면 이제 그 안에서 중요한 개념과 규칙을 코드로 표현할 차례다. 이것이 **도메인 모델**이다.

도메인 모델은 현실의 모든 정보를 복사한 데이터 모음이 아니다. 현재 해결하려는 문제에 필요한 상태와 행동을 추려 표현한 모델이다. 주문 컨텍스트라면 주문 번호, 주문 상태와 주문 상품이 필요하고, `배송이 시작된 주문은 취소할 수 없다`는 규칙도 함께 필요하다.

처음에는 다음처럼 상태를 직접 바꾸는 코드를 작성할 수 있다.

```java
order.setStatus(OrderStatus.CANCELED);
```

이 한 줄만으로는 누가 어떤 상태에서 취소할 수 있는지 알 수 없다. 호출하는 모든 코드가 취소 규칙을 따로 기억해야 한다. DDD의 전술적 패턴은 이런 업무 의미와 규칙을 모델 안에 남길 때 사용할 수 있는 도구다.

### Entity는 식별자로 이어진다

**Entity**는 속성이 바뀌어도 같은 대상으로 계속 추적해야 하는 객체다.

주문의 배송지와 상태는 바뀔 수 있다. 그래도 주문 번호가 같다면 어제 조회한 주문과 오늘 조회한 주문은 같은 주문이다. Entity는 현재 속성 전체보다 `어떤 대상을 계속 추적하는가`가 중요하다.

```java
public class Order {

    private final OrderId id;
    private OrderStatus status;

    public void cancel() {
        if (!status.isCancelable()) {
            throw new IllegalStateException(
                "현재 상태에서는 주문을 취소할 수 없습니다."
            );
        }

        status = OrderStatus.CANCELED;
    }
}
```

외부에서 상태를 마음대로 바꾸지 않고 `cancel()`을 거치게 했다. 이제 주문을 취소하는 의미와 취소할 수 있는 조건을 `Order`가 함께 보여준다.

> **Entity를 볼 때의 질문:** 속성이 달라져도 같은 대상으로 추적해야 하는가?

### Value Object는 값으로 의미를 표현한다

**Value Object**는 고유한 식별자보다 값 자체가 중요한 객체다. 금액, 주소와 기간이 대표적이다.

주문 금액을 `BigDecimal` 하나로만 사용하면 그 숫자의 단위와 허용 범위를 매번 주변 코드에서 확인해야 한다. 프로젝트가 원화만 다룬다고 가정하고 `Money`로 묶으면 금액이라는 의미와 규칙을 한곳에 둘 수 있다.

```java
public record Money(BigDecimal amount) {

    public Money {
        Objects.requireNonNull(amount);

        if (amount.signum() < 0) {
            throw new IllegalArgumentException(
                "금액은 음수일 수 없습니다."
            );
        }
    }

    public Money add(Money other) {
        return new Money(amount.add(other.amount));
    }
}
```

같은 금액을 가진 두 `Money`는 같은 값으로 볼 수 있다. 주문처럼 생성된 뒤 상태가 바뀌는 대상을 추적하는 Entity와 달리, Value Object는 값 전체가 의미를 결정한다. 그래서 불변 객체로 만드는 경우가 많다.

> **Value Object를 볼 때의 질문:** 여러 값이나 규칙을 하나의 도메인 개념으로 다룰 수 있는가?

### Aggregate는 함께 지킬 규칙의 범위를 정한다

주문에는 여러 주문 상품과 배송지가 들어 있다. 주문 상품의 수량을 바꾸면 총금액도 다시 계산해야 하고, 이미 취소한 주문이라면 수량 변경을 막아야 한다.

외부 코드가 `OrderLine`을 직접 꺼내 수량만 바꾸면 총금액 재계산을 놓칠 수 있다. 관련 객체를 단순히 한곳에 모으는 것만으로는 부족하다. 어디를 통해 변경해야 규칙을 빠뜨리지 않을지도 정해야 한다.

**Aggregate**는 한 번의 변경에서 함께 일관성을 지켜야 하는 객체의 묶음이다. 외부에서는 **Aggregate Root**를 통해서만 내부 상태를 변경한다. 주문 Aggregate에서는 `Order`가 Root가 된다.

```java
public void changeQuantity(OrderLineId lineId, int quantity) {
    if (status == OrderStatus.CANCELED) {
        throw new IllegalStateException(
            "취소된 주문은 수량을 바꿀 수 없습니다."
        );
    }

    OrderLine line = findOrderLine(lineId);
    line.changeQuantity(quantity);
    totalPrice = calculateTotalPrice();
}
```

![Order가 Aggregate Root가 되어 주문 상품과 배송지 변경을 통제하는 구조](/images/posts/domain-driven-design/order-aggregate.svg "주문 Aggregate의 구조")

*주문 Aggregate와 그 안에서 함께 지켜야 할 규칙*

Aggregate를 크게 잡을수록 좋은 것은 아니다. 한 번에 지켜야 할 규칙이 아닌 객체까지 묶으면 매번 많은 데이터를 불러오고 수정하게 된다. 반대로 너무 작게 나누면 하나의 규칙을 여러 Aggregate에 걸쳐 즉시 지키기 어려워진다.

> **Aggregate를 볼 때의 질문:** 한 번의 변경에서 반드시 함께 일관성을 지켜야 하는 범위는 어디까지인가?

이제 세 용어의 차이를 한 번에 비교할 수 있다.

| 개념 | 구분하는 기준 | 주문 예시 |
|---|---|---|
| Entity | 식별자로 같은 대상을 추적 | `Order`, `OrderLine` |
| Value Object | 값 자체가 의미를 결정 | `Money`, `ShippingAddress` |
| Aggregate | 함께 일관성을 지킬 변경 범위 | `Order`와 내부 주문 항목 |

## 애플리케이션은 도메인 모델을 사용한다

도메인 모델이 업무를 판단하더라도 HTTP 요청을 받고, 주문을 불러오고, 트랜잭션을 시작하는 코드는 여전히 필요하다.

주문 취소 요청은 다음처럼 흐를 수 있다.

```text
Controller
    ↓
CancelOrderService
    ↓
Order.cancel()
    ↓
OrderRepository
```

`CancelOrderService` 같은 **응용 서비스**는 하나의 사용 사례를 완성하는 순서를 조정한다. 주문을 취소할 수 있는지는 `Order`가 판단하고, 응용 서비스는 주문을 조회해 취소를 요청한 뒤 저장한다.

```java
@Service
@RequiredArgsConstructor
public class CancelOrderService {

    private final OrderRepository orderRepository;

    @Transactional
    public void cancel(OrderId orderId) {
        Order order = orderRepository.findById(orderId)
            .orElseThrow(OrderNotFoundException::new);

        order.cancel();
        orderRepository.save(order);
    }
}
```

여기서 `배송을 시작한 주문은 취소할 수 없다`는 조건을 응용 서비스가 다시 `if`문으로 판단하지 않는다. 같은 주문 취소가 관리자 기능과 자동 처리에서도 사용되더라도 규칙은 `Order.cancel()`에 남아 있다.

### Repository는 Aggregate를 저장하고 불러온다

**Repository**는 Aggregate를 저장하고 다시 불러오는 방법을 제공한다. 도메인 코드는 주문이 어느 테이블에 어떤 칼럼으로 저장되는지보다 주문을 찾고 저장할 수 있다는 사실에 집중한다.

```java
public interface OrderRepository {

    Optional<Order> findById(OrderId orderId);

    void save(Order order);
}
```

Repository는 보통 Aggregate Root 단위로 만든다. `orders`와 `order_lines` 테이블이 따로 있다는 이유만으로 각각을 독립적으로 수정하는 Repository를 만들면, `Order`가 지키던 변경 규칙을 우회할 수 있기 때문이다.

JPA로 어떻게 저장할지는 Repository 구현이 맡을 수 있다. 그렇다고 DDD를 하려면 도메인 객체와 JPA Entity를 반드시 분리해야 한다는 뜻은 아니다. 복잡성과 변경 가능성을 고려해 같은 객체를 사용할 수도 있고 분리할 수도 있다. 중요한 것은 저장 방식 때문에 도메인 규칙을 표현하기 어려워지지 않는가다.

### 어느 객체에도 자연스럽게 속하지 않는 규칙

모든 규칙을 억지로 Entity에 넣을 수는 없다. 회원 등급과 주문 금액을 함께 사용해 할인을 계산하는 것처럼 여러 도메인 객체가 필요하고 어느 한쪽의 책임이라고 보기 어려운 규칙이 있다.

이런 규칙은 **Domain Service**로 표현할 수 있다.

```java
public class DiscountPolicy {

    public Money calculate(Member member, Order order) {
        if (member.isVip()) {
            return order.totalPrice()
                .multiply(new BigDecimal("0.10"));
        }

        return Money.ZERO;
    }
}
```

다만 Entity가 스스로 판단할 수 있는 규칙까지 전부 Domain Service로 옮기면 도메인 객체는 다시 데이터만 담게 된다. 먼저 규칙과 가장 가까운 Entity나 Value Object가 맡을 수 있는지 살펴보는 편이 좋다.

## 다른 경계와 협력한다

주문, 결제와 배송을 서로 다른 바운디드 컨텍스트로 나눴다고 협력이 사라지는 것은 아니다. 오히려 무엇을 주고받을지 명확하게 정해야 한다.

주문 컨텍스트가 결제 컨텍스트의 Entity를 직접 변경하는 대신, 환불 요청 API를 호출하거나 주문이 취소됐다는 사실을 알릴 수 있다.

**Domain Event**는 도메인에서 이미 일어난 의미 있는 사건을 표현한다.

```java
public record OrderCanceled(
    OrderId orderId,
    Money refundAmount,
    Instant occurredAt
) {
}
```

결제 컨텍스트는 이 사건을 받아 환불을 시작하고, 쿠폰 컨텍스트는 사용한 쿠폰을 복구할 수 있다. 주문 Aggregate는 자신이 알 필요 없는 후속 처리와 직접 결합되지 않는다.

이벤트라고 반드시 Kafka나 비동기 처리가 필요한 것은 아니다. 같은 애플리케이션 안에서 동기적으로 전달할 수도 있다. 메시지 큐를 사용해 외부 시스템으로 전달한다면 이벤트 유실과 중복, DB 트랜잭션과의 불일치까지 별도로 설계해야 한다.

다른 컨텍스트의 모델을 받아들일 때는 자신의 언어로 변환하기도 한다. 결제 시스템의 `PaymentResponse`를 주문 컨텍스트의 `RefundResult`로 바꾸면 외부 모델의 변경이 주문 모델 안쪽까지 그대로 퍼지는 일을 줄일 수 있다. 이런 변환 경계를 **부패 방지 계층**이라고 부른다.

## DDD와 함께 보이지만 같은 것은 아니다

DDD를 공부하다 보면 헥사고날 아키텍처, CQRS, 이벤트 기반 아키텍처와 MSA가 함께 등장한다. 서로 잘 어울리는 선택지이지만 DDD 그 자체는 아니다.

- **헥사고날·클린 아키텍처:** 도메인과 외부 기술 사이의 의존성을 통제하는 구조
- **CQRS:** 상태를 변경하는 모델과 조회하는 모델을 분리하는 방식
- **이벤트 기반 아키텍처:** 사건을 중심으로 시스템이 협력하는 방식
- **MSA:** 서비스를 독립적인 배포와 운영 단위로 나누는 구조

DDD는 모놀리식 애플리케이션에도 적용할 수 있고, JPA Entity를 도메인 Entity로 함께 사용할 수도 있다. 반대로 패키지 이름만 `domain`으로 바꾸고 Entity와 Aggregate를 만들었다고 업무 이해가 깊어지는 것도 아니다.

DDD의 중심은 패턴의 개수가 아니라 다음 흐름이다.

```text
업무를 함께 이해한다
→ 같은 언어를 사용한다
→ 모델이 유효한 경계를 정한다
→ 업무 규칙을 모델과 코드에 남긴다
```

## DDD는 언제 도움이 될까?

DDD는 업무가 복잡할수록 가치가 커진다.

- 하나의 용어를 팀마다 다르게 이해함
- 상태와 예외 규칙이 많아 변경할 때마다 빠뜨리는 조건이 생김
- 중요한 규칙이 여러 Service와 배치 코드에 흩어짐
- 데이터 구조보다 업무의 변화가 시스템을 더 자주 흔듦
- 개발자만으로 정확한 규칙을 정하기 어려워 업무 담당자와 지속적인 협업이 필요함

반대로 단순한 관리자 CRUD나 외부 데이터를 그대로 전달하는 기능이라면 풍부한 도메인 모델이 얻는 이점보다 코드와 학습 비용이 더 클 수 있다. 이때는 평범한 레이어드 구조와 단순한 데이터 모델로도 충분하다.

핵심 서브도메인에는 깊은 모델링을 적용하고, 일반 서브도메인은 단순하게 구현할 수도 있다. DDD를 도입한다는 말이 시스템 전체를 한 번에 같은 구조로 바꾼다는 뜻은 아니다.

## 정리

주문 취소 기능의 문제는 처음부터 코드에만 있지 않았다. `취소`라는 말을 각 팀이 다르게 이해했고, 어느 업무가 무엇을 판단해야 하는지 경계도 흐렸다.

DDD는 먼저 도메인 전문가와 개발자가 **유비쿼터스 언어**로 업무를 이해하게 한다. 그다음 **서브도메인**과 **바운디드 컨텍스트**로 모델이 통하는 경계를 찾는다.

경계 안에서는 다음 전술적 패턴으로 업무 규칙을 코드에 남길 수 있다.

- **Entity:** 식별자로 같은 대상을 계속 추적
- **Value Object:** 값 자체로 도메인의 의미를 표현
- **Aggregate:** 한 번의 변경에서 함께 지킬 일관성의 범위
- **Repository:** Aggregate를 저장하고 다시 불러오는 계약
- **Domain Service:** 어느 한 객체에 자연스럽게 속하지 않는 도메인 규칙
- **Domain Event:** 도메인에서 이미 일어난 의미 있는 사건

결국 DDD는 용어를 많이 사용하는 설계가 아니다. 복잡한 업무를 같은 언어로 이해하고, 그 이해가 문서에서 끝나지 않도록 모델과 코드에 이어가는 과정이다.
