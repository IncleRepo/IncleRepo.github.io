조회수 기능은 숫자 하나를 올리는 일처럼 보인다. 하지만 실제로는 서로 다른 두 문제를 함께 해결해야 한다.

첫째는 여러 요청이 동시에 값을 올릴 때 증가분이 사라지지 않게 하는 **동시성 문제**다. 둘째는 같은 사용자의 반복 조회를 몇 번으로 계산할지 정하는 **업무 정책 문제**다. Lock을 건다고 중복 조회가 사라지지 않고, Cookie를 둔다고 Lost Update가 해결되지도 않는다.

예를 들어 서로 다른 사용자 두 명이 동시에 글을 읽었다면 조회수는 반드시 2 증가해야 한다. 반면 같은 사용자가 새로 고침을 열 번 했다면 이를 10으로 셀지 1로 셀지는 서비스가 정할 문제다. 첫 번째는 계산의 정확성이고 두 번째는 조회의 정의다.

## 먼저 원자적으로 증가시켜야 한다

가장 위험한 구현은 값을 읽고 Java에서 1을 더한 뒤 다시 저장하는 방식이다.

```text
요청 A: 조회수 10 읽기 → 11 저장
요청 B: 조회수 10 읽기 → 11 저장
결과: 두 번 조회했지만 11
```

이 현상을 Lost Update라고 한다. 단순한 Counter라면 데이터베이스가 한 문장으로 값을 증가시키게 만드는 편이 가장 간단하다.

```sql
UPDATE post
   SET view_count = view_count + 1
 WHERE id = ?;
```

같은 행을 변경하는 `UPDATE`는 데이터베이스의 Lock과 원자적 연산 안에서 처리된다. 현재 값을 애플리케이션으로 가져왔다가 다시 저장하지 않으므로 읽기와 쓰기 사이의 경쟁 구간도 사라진다.

조회수 외의 상태를 읽고 복잡한 판단까지 해야 한다면 `SELECT ... FOR UPDATE`나 낙관적 Lock을 검토할 수 있다. 하지만 단순 Counter에 비관적 Lock 조회를 먼저 추가하면 SQL과 Lock 보유 시간만 늘어날 수 있다.

이렇게 증가 연산을 안전하게 만들어도 같은 사용자의 새로 고침을 몇 번으로 셀지는 해결되지 않는다. 동시성 제어와 별개로 한 번의 조회를 정의하는 업무 정책이 필요하다.

## 중복 조회는 먼저 정책을 정해야 한다

“한 사용자는 한 번만 증가”라고 말해도 사용자와 한 번의 뜻이 분명하지 않다.

- 로그인 Account 기준인가
- 브라우저 Cookie 기준인가
- IP 기준인가
- 하루에 한 번인가, 게시글 수명 동안 한 번인가
- 새로 고침과 다른 기기 접속을 어떻게 볼 것인가

로그인 서비스라면 Account ID가 가장 분명하지만 비로그인 사용자를 다룰 수 없다. Cookie는 구현이 간단하지만 사용자가 삭제하거나 다른 브라우저를 쓰면 새 방문으로 보인다. IP는 여러 사용자가 같은 공인 IP를 공유할 수 있고 Proxy 환경에서도 신뢰하기 어렵다.

즉, 기술을 고르기 전에 허용할 오차를 먼저 정해야 한다. 완벽한 사람 식별이 필요하지 않은 일반 조회수라면 “브라우저별 하루 한 번”처럼 설명 가능한 정책이 현실적이다.

식별 기준과 기간이 정해지면 이를 어디에 기록할지 선택할 수 있다. 먼저 별도 인프라 없이 데이터베이스의 제약 조건으로 중복을 막는 구조를 살펴보자.

## 데이터베이스만 사용하는 방식

중복 조회 기록을 별도 테이블에 저장하고 Unique Constraint로 막을 수 있다.

```sql
CREATE TABLE post_view (
    post_id BIGINT NOT NULL,
    viewer_key VARCHAR(100) NOT NULL,
    viewed_date DATE NOT NULL,
    PRIMARY KEY (post_id, viewer_key, viewed_date)
);
```

동일한 조합은 한 번만 INSERT되므로 여러 요청이 동시에 들어와도 데이터베이스가 중복을 막는다. INSERT에 성공한 요청만 조회수를 증가시키면 된다.

두 작업은 같은 트랜잭션에서 처리해야 한다.

```text
post_view INSERT 성공
→ post.view_count 원자적 증가
→ 함께 Commit

post_view INSERT가 중복으로 실패
→ 이미 센 조회이므로 증가하지 않음
```

INSERT만 Commit되고 조회수 증가가 실패하거나, 조회수만 증가하고 중복 기록이 Rollback되면 다음 요청에서 다시 증가할 수 있다. 하나의 데이터베이스를 사용하는 구조의 장점은 이 두 변경을 같은 트랜잭션으로 묶을 수 있다는 점이다.

이 방식은 정합성이 분명하고 별도 인프라가 필요 없다. 반면 조회량이 매우 많으면 중복 기록 테이블이 빠르게 커지고, 게시글 조회마다 쓰기가 발생한다.

실제 쓰기 부하가 이 단순한 구조의 한계를 넘는다면 짧은 수명의 중복 Key와 빠른 Counter를 Redis로 옮길 수 있다. 대신 데이터베이스가 제공하던 내구성과 원자성의 일부를 애플리케이션이 다시 설계해야 한다.

## Redis를 사용하는 방식

Redis에서는 기간이 있는 중복 Key와 Counter를 따로 관리할 수 있다.

```text
viewed:post:{postId}:{viewerKey} = 1, TTL 1일
views:post:{postId} = 누적 증가분
```

`SET key value NX EX seconds`로 중복 Key가 처음 생성된 경우에만 `INCR`를 수행한다. 여러 명령을 하나의 원자적 단위로 묶어야 한다면 Lua Script나 Redis Transaction을 검토한다.

`NX`는 Key가 없을 때만 저장하라는 조건이고, `EX`는 초 단위 TTL이다. 반환값으로 처음 조회인지 구분할 수 있다.

```text
SET viewed:post:100:member:15 1 NX EX 86400
→ OK   : 오늘 처음 조회, Counter 증가
→ nil  : 이미 존재, 증가하지 않음
```

하지만 `SET NX`가 성공한 직후 `INCR` 전에 프로세스가 종료되면 중복 Key만 남고 조회수는 증가하지 않는다. 두 명령을 반드시 함께 적용해야 한다면 Lua Script처럼 Redis 안에서 하나의 원자적 작업으로 실행해야 한다.

Redis의 `INCR`는 Counter 증가를 원자적으로 수행한다. DB에 매 조회를 즉시 쓰지 않고 Redis에 모았다가 일정 주기로 반영하면 쓰기 부하를 줄일 수 있다.

그러나 이 구조는 새로운 질문을 만든다.

- 동기화 직전 Redis나 프로세스에 장애가 나면 증가분을 잃어도 되는가
- DB 반영에 성공했지만 Redis Counter 초기화 전에 실패하면 중복 반영되지 않는가
- 화면에는 Redis와 DB 중 어느 값을 보여줄 것인가
- 재처리할 수 있도록 마지막 반영 지점을 어떻게 기록할 것인가

조회수처럼 약간의 지연과 오차를 허용할 수 있는 지표라면 이 절충이 합리적일 수 있다. 과금이나 재고처럼 정확한 수치에는 같은 방식을 그대로 적용하면 안 된다.

특히 증가분을 Redis에 모으는 순간 “나중에 DB에 반영한다”는 별도의 작업이 생긴다. 성능을 얻으려면 정상 흐름뿐 아니라 반영 도중 실패했을 때 어디서 다시 시작할지도 정해야 한다.

## 지연 반영은 복구 기준까지 설계해야 한다

Redis Counter를 사용하면 여러 조회의 증가분을 모아 데이터베이스에 한 번에 반영할 수 있다.

```text
조회 요청 → Redis INCR
              ↓ 일정 주기
처리할 증가분 분리 → DB의 view_count에 증가분 반영 → 처리 완료
```

이 구조는 데이터베이스 쓰기 횟수를 줄이지만, Redis 값을 읽어 DB에 더한 뒤 Key를 지우는 세 단계가 자동으로 하나의 트랜잭션이 되지는 않는다.

- DB 반영에 성공하고 Redis 정리 전에 실패하면 같은 증가분을 다시 더할 수 있다.
- Redis 값을 읽은 뒤 정리하기 전에 새 조회가 들어오면 새 증가분까지 함께 지울 수 있다.
- 처리 중인 증가분을 애플리케이션 메모리에만 들고 있다가 프로세스가 종료되면 복구할 위치가 없다.

따라서 새 요청이 쌓이는 Counter와 현재 반영 중인 증가분을 분리하고, 실패한 증가분이 Redis에 남아 다시 처리될 수 있게 해야 한다. 같은 반영 묶음을 두 번 적용하지 않도록 Batch 식별자나 마지막 반영 지점도 필요할 수 있다. 구체적인 구현보다 중요한 것은 **어떤 증가분이 대기 중이고, 처리 중이며, 반영 완료됐는지를 구분할 수 있는가**다.

한 가지 사고 방식은 현재 Counter를 처리용 Key로 원자적으로 옮긴 뒤 새 조회는 빈 Counter에 계속 받는 것이다.

```text
views:post:100 = 37
→ 처리 시작 시 processing:views:post:100:batch-21로 분리
→ views:post:100은 다시 0부터 새 증가분 수집
→ DB에 37 반영
→ 성공하면 processing Key 삭제
→ 실패하면 processing Key를 남겨 재시도
```

이 예시는 특정 구현을 강제하려는 것이 아니다. 새 증가분과 이미 DB에 반영 중인 증가분을 같은 숫자 하나로 다루면 삭제·재시도 시점을 구분하기 어렵다는 점을 보여준다.

조회수처럼 약간의 지연을 허용할 수 있어야 이 복잡성을 감수할 이유가 생긴다. 데이터베이스의 원자적 `UPDATE`만으로 처리량이 충분하다면 지연 반영을 먼저 도입할 필요는 없다.

따라서 처음부터 가장 복잡한 구조를 고르는 것이 아니라 요구되는 정확도와 확인된 부하에 맞춰 단계를 올리는 편이 낫다. 앞에서 나눈 증가, 중복 방지와 지연 반영을 하나의 선택 순서로 정리할 수 있다.

## 어떤 구조를 선택할까

트래픽이 크지 않다면 먼저 단일 `UPDATE`와 데이터베이스 Unique Constraint로 시작하는 편이 단순하다. 실제 쓰기 부하가 병목으로 확인됐을 때 Redis Counter와 비동기 반영을 도입해도 늦지 않다.

중복 방지와 증가 연산을 하나의 문제처럼 풀면 구현이 복잡해진다. 다음 순서로 나누면 선택이 쉬워진다.

1. 한 번의 조회를 어떻게 정의할지 결정한다.
2. 같은 조회를 식별할 Key와 기간을 정한다.
3. 증가 연산을 원자적으로 만든다.
4. 지연 반영을 사용한다면 대기·처리·완료 상태와 재시도 기준을 정한다.

## 정리

- Lost Update와 중복 조회는 서로 다른 문제다.
- 단순 Counter는 값을 읽어 덮어쓰기보다 `view_count = view_count + 1` 형태의 원자적 변경이 낫다.
- 로그인 ID, Cookie와 IP는 식별 정확도와 비용이 다르다.
- DB Unique Constraint는 단순하고 강한 중복 방지 수단이다.
- Redis 지연 반영은 부하를 줄이지만 증가분의 대기·처리·완료 상태와 재시도 기준이 필요하다.
