현재 조회수가 10인 글이 있다. 사용자 A가 글을 조회하는 순간 사용자 B도 같은 글을 조회했다.

```text
현재 조회수 = 10

사용자 A가 글 조회
사용자 B도 동시에 글 조회

기대 결과
→ 조회수 12
```

숫자 하나를 두 번 올리는 일이라 간단해 보이지만, 여기서 서로 다른 두 질문이 생긴다.

```text
질문 1

A와 B의 증가분이 모두 반영되는가?
→ 두 요청이 들어왔다면 숫자가 정확히 2 증가해야 함


질문 2

A와 B가 사실 같은 사람이라면 어떻게 셀 것인가?
→ 새로 고침 10번을 조회 10번으로 볼지 결정해야 함
```

첫 번째는 여러 요청이 같은 값을 수정할 때 생기는 **동시성 문제다.**
두 번째는 무엇을 한 번의 조회로 볼 것인지 정하는 **업무 정책 문제다.**

```text
조회수 중복 문제
→ 무조건 Lock

Cookie로 반복 조회 방지
→ 동시성 문제까지 해결
```

Lock과 Cookie는 서로 다른 문제를 해결한다. Lock은 증가분이 서로 덮이는 일을 막고, Cookie는 같은 사용자의 반복 조회를 구분하는 데 사용한다.

이 글에서는 다음 순서로 문제를 하나씩 분리한다.

```text
증가 연산의 정확성
→ 한 번의 조회를 정의하는 정책
→ DB에서 중복 기록
→ Redis로 쓰기 부하 이동
→ Redis 명령 사이의 실패 구간
→ 증가분을 DB에 지연 반영
→ 재시도와 중복 반영 방지
```

## 1. 조회 두 번의 증가분이 모두 남아야 한다

가장 먼저 해결할 것은 A와 B가 서로 다른 정상 조회인데도 숫자가 한 번만 증가하는 문제다.

### 두 요청 모두 성공했는데 결과가 틀릴 수 있다

조회수를 Entity에서 읽어 Java로 1을 더한 뒤 저장한다고 해보자.

```text
요청 A: 조회수 10 읽기 → Java에서 11 계산 → 11 저장
요청 B: 조회수 10 읽기 → Java에서 11 계산 → 11 저장

결과
→ 조회는 두 번
→ 조회수는 11
```

두 요청 모두 예외 없이 정상 처리됐다. Rollback도 발생하지 않았다. 그런데 한쪽의 증가 결과가 다른 요청에 덮여 사라졌다.

이처럼 동시에 같은 값을 수정하면서 한쪽 변경이 덮여 사라지는 현상을 `Lost Update`라고 한다.

문제는 애플리케이션과 DB가 받아들인 명령의 차이에서 더 분명하게 보인다.

```text
애플리케이션이 생각한 작업

"현재 조회수에서 1 증가"


DB가 실제로 받은 작업

"view_count에 11을 저장"
```

두 요청은 각각 다음과 같은 SQL을 보낼 수 있다.

```sql
UPDATE post
   SET view_count = 11
 WHERE id = ?;
```

둘 다 현재 값 10을 기준으로 계산했기 때문에 DB에는 같은 최종 값 11을 저장한다. 이제 계산을 Java에서 하지 않고 DB 안으로 옮겨보자.

### DB가 현재 값에서 직접 증가시킨다

```sql
UPDATE post
   SET view_count = view_count + 1
 WHERE id = ?;
```

이제 애플리케이션이 현재 조회수를 먼저 읽지 않는다. DB가 해당 행의 현재 값을 기준으로 직접 1을 더한다.

```text
기존

SELECT로 현재 값 읽기
↓
Java에서 +1 계산
↓
계산 결과 UPDATE


개선

UPDATE 안에서
현재 값 + 1
```

InnoDB에서는 같은 행을 수정하는 `UPDATE`가 겹치면 먼저 행을 변경한 Transaction이 가진 Lock이 끝날 때까지 다음 변경이 기다린다. 이후 요청은 앞선 변경이 반영된 값을 기준으로 다시 증가시킨다.

```text
현재 조회수 10

요청 A의 UPDATE
→ 11

요청 B의 UPDATE
→ A가 끝난 뒤 현재 값 11에서 증가
→ 12
```

**이처럼 현재 값을 DB 안에서 하나의 변경 연산으로 증가시키는 방식을 여기서는 원자적 UPDATE라고 하겠다.** 읽기와 쓰기 사이에 다른 요청이 끼어들어 증가분이 사라지는 구간을 없앨 수 있다.

### 단순 Counter라면 Lock 조회부터 추가하지 않는다

동시성 문제가 보이면 바로 `SELECT ... FOR UPDATE` 같은 비관적 Lock부터 떠올리기 쉽다. 하지만 조회수처럼 단순히 1을 더하는 작업은 현재 값을 Java에서 읽을 필요가 없다.

```text
단순 조회수 +1

현재 값을 Java에서 판단할 필요 없음
→ UPDATE 한 문장으로 표현 가능


재고 차감 같은 복잡한 업무

현재 재고 확인
주문 수량 비교
품절 여부 판단
여러 값 변경
→ 읽고 판단하는 과정 필요
→ Lock이나 Version 검토 가능
```

가장 강한 동시성 제어부터 넣기보다 업무를 정확하게 표현할 수 있는 가장 작은 수단부터 검토한다. 단순 Counter에서는 원자적 UPDATE가 먼저다.

다만 같은 게시글 한 행에 매우 많은 UPDATE가 몰리면 요청들이 그 행의 Lock을 기다리며 병목이 될 수 있다. 정확성 문제를 해결한 것과 높은 처리량을 확보한 것은 또 다른 문제다. 이 차이는 뒤에서 Redis를 검토할 때 다시 살펴본다.

여기까지 해결된 것은 **서로 다른 두 조회의 증가분이 사라지지 않게 만든 것뿐이다.** 같은 사람이 새로 고침을 10번 하면 원자적 UPDATE는 정확하게 10번 증가한다. 서비스가 이를 한 번으로 세고 싶다면 이제 기술이 아니라 조회의 의미부터 정해야 한다.

## 2. 무엇을 한 번의 조회로 볼지 정한다

“한 사용자는 한 번만 증가시킨다”는 문장은 생각보다 모호하다. 먼저 두 기준으로 나누면 정책이 선명해진다.

```text
누구를 같은 사용자로 볼 것인가?
+
얼마 동안 같은 조회로 볼 것인가?
```

### 사용자를 구분하는 기준

| 식별 기준 | 얻는 점 | 한계 |
|---|---|---|
| Account ID | 로그인 사용자를 비교적 명확하게 구분 | 비로그인 사용자는 Account만으로 구분할 수 없음 |
| Browser Cookie | 비로그인 사용자도 브라우저 단위로 어느 정도 구분 | 삭제 가능하며 브라우저와 기기가 달라지면 다른 사용자처럼 보임 |
| IP 주소 | 별도 식별 값을 발급하지 않아도 사용 가능 | NAT·Proxy 환경에서 여러 사용자가 같은 공인 IP를 공유할 수 있음 |

어떤 기준도 실제 사람 한 명을 완벽하게 식별하지는 못한다. Account는 로그인 범위에서 강하지만 다른 계정과 비로그인 사용자가 남는다. Cookie는 구현이 단순하지만 클라이언트가 지울 수 있다. IP는 공유 네트워크에서 서로 다른 사람을 한 명으로 묶을 수 있다.

따라서 정답을 찾기보다 서비스가 받아들일 오차를 고른다. 조회수처럼 약간의 오차를 허용할 수 있다면 “브라우저별로 계산한다”처럼 설명 가능한 정책이 현실적일 수 있다.

### 같은 조회로 볼 기간

사용자 기준만으로는 부족하다. 같은 사람이 언제 다시 방문했을 때 새로운 조회로 셀지도 정해야 한다.

```text
매 요청마다 증가
1분 동안 한 번
1시간 동안 한 번
하루에 한 번
게시글 전체 기간에 한 번
```

결국 중복 조회 정책은 다음 두 요소의 조합이다.

```text
식별 기준 + 중복 제한 기간

예시
Browser Cookie + 24시간에 한 번
Account ID + 달력 날짜별 한 번
```

`viewerKey`는 이 정책에 따라 동일 사용자를 어느 정도 구분하기 위한 식별 값이다. Account ID, Cookie에서 만든 식별자 등이 들어갈 수 있다.

완벽한 식별보다 중요한 것은 정책을 명확하게 설명하는 일이다. 이제 누구를 얼마 동안 같은 조회로 볼지 정했다. 다음 문제는 이미 센 조회인지 어디에 기록할 것인가다. 먼저 Redis 없이 DB만으로 구현해보자.

## 3. DB 제약 조건으로 중복 조회를 막는다

오늘 Member 15가 Post 100을 이미 봤는지 기억하려면 조회 기록 하나를 남길 수 있다.

```text
Post 100
+ Member 15
+ 오늘 날짜

이 조합의 기록 있음
→ 이미 센 조회

기록 없음
→ 첫 조회
```

이를 테이블로 만들면 다음과 같다.

```sql
CREATE TABLE post_view (
    post_id BIGINT NOT NULL,
    viewer_key VARCHAR(100) NOT NULL,
    viewed_date DATE NOT NULL,
    PRIMARY KEY (post_id, viewer_key, viewed_date)
);
```

`(post_id, viewer_key, viewed_date)` 조합은 한 번만 저장할 수 있다. 같은 조회 기록을 두 번 저장하지 못하게 하는 이런 규칙을 `Primary Key` 또는 `Unique Constraint`, 즉 고유 제약 조건으로 표현할 수 있다.

### 사전 조회만으로는 동시 중복 INSERT를 막지 못한다

애플리케이션에서 먼저 기록 존재 여부를 확인할 수도 있다.

```text
SELECT로 기록 확인
↓
없음
↓
INSERT
```

하지만 같은 요청 두 개가 동시에 들어오면 둘 다 기록이 없다고 판단할 수 있다.

```text
요청 A: 없음 확인
요청 B: 없음 확인

요청 A: INSERT
요청 B: INSERT
```

애플리케이션의 사전 확인은 동시 요청 사이에서 달라질 수 있다. 최종적으로 DB가 중복 INSERT 자체를 거부할 수 있어야 한다. MySQL은 Primary Key나 Unique Key를 위반하는 변경문을 오류로 처리하므로 동시에 시도해도 같은 조합은 하나만 남는다.

실제 구현에서는 INSERT 성공 여부나 중복 키 오류를 기준으로 첫 조회를 구분할 수 있다. `INSERT IGNORE` 같은 문법을 쓴다면 중복 외의 오류까지 숨기지 않는지와 실제 반영 행 수를 함께 확인해야 한다.

### 중복 기록과 Counter 증가는 같이 끝나야 한다

첫 조회라면 두 가지 변경이 필요하다.

```text
1. post_view에 중복 조회 기록 INSERT
2. post.view_count를 1 증가
```

두 SQL을 단순히 연속으로 실행하는 것만으로는 부족하다. 첫 작업만 성공한 뒤 두 번째 작업이 실패할 수 있다.

```text
post_view INSERT 성공
↓
view_count UPDATE 실패

결과
→ 이미 본 사용자로 기록됨
→ 조회수는 증가하지 않음
→ 다음 요청도 중복으로 판단되어 복구되지 않음
```

반대 순서에서도 문제가 생긴다.

```text
view_count 증가 성공
↓
post_view INSERT 실패 또는 Rollback

결과
→ 조회수는 증가함
→ 조회 기록은 없음
→ 다음 요청에서 다시 증가할 수 있음
```

중복 조회 기록과 조회수 증가를 하나의 업무 단위로 본다면 둘은 같이 Commit되거나 같이 Rollback되어야 한다.

```text
Transaction 시작
↓
post_view INSERT 성공
↓
post.view_count 원자적 증가
↓
둘 다 Commit

중간 실패
→ 둘 다 Rollback
```

하나의 InnoDB 데이터베이스를 사용할 때 얻는 큰 장점이다. DB가 중복 제약과 Transaction을 함께 제공하므로 구조가 단순하다.

### DB만으로 충분하다면 여기서 끝내도 된다

| 장점 | 비용 |
|---|---|
| 고유 제약 조건이 동시 중복 INSERT를 막는다. | 첫 조회마다 `post_view` INSERT가 발생한다. |
| 기록과 Counter 증가를 같은 Transaction으로 묶을 수 있다. | 첫 조회마다 `post` Counter UPDATE가 발생한다. |
| 별도 Redis 인프라와 복구 흐름이 필요 없다. | 조회 기록 테이블이 계속 커질 수 있다. |
| 데이터의 기준이 DB 하나라 이해하기 쉽다. | 인기 게시글 하나에 UPDATE가 집중되면 같은 행의 Lock 대기가 늘 수 있다. |

이 비용이 실제 병목으로 확인되지 않았다면 DB 방식으로 충분하다. 필요한 정확성과 처리량을 가장 단순하게 만족하는 구조이기 때문이다.

실제 측정에서 조회 기록 INSERT나 인기 행 UPDATE가 병목으로 확인됐다면 Redis로 일부 역할을 옮길 수 있다. DB 구조가 감당하기 어려운 쓰기 부하를 Redis가 나누어 맡는 선택이다.

## 4. 실제 DB 쓰기 병목이 생기면 Redis를 검토한다

Redis에서는 두 역할을 별도의 Key로 나눈다.

```text
중복 방지용 Key

viewed:post:{postId}:{viewerKey}
→ 이 사용자의 조회를 이미 셌는지 기록


조회수 증가용 Counter

views:post:{postId}
→ 아직 DB에 반영하지 않은 증가분 누적
```

하나의 Redis Key가 중복 판단과 숫자 누적을 모두 해결하는 것이 아니다. 첫 번째 Key는 “이미 셌는가?”를 표현하고, 두 번째 Counter는 “몇 번 증가했는가?”를 표현한다.

### 처음 본 경우에만 중복 Key를 만든다

요구사항을 먼저 문장으로 적어보자.

> 오늘 이 사용자가 이 글을 처음 본 경우에만 Key를 만들고 싶다.

Redis의 `SET` 명령에 `NX`와 `EX` 조건을 함께 사용하면 이를 표현할 수 있다.

```redis
SET viewed:post:100:member:15 1 NX EX 86400
```

```text
Key 없음
→ 저장 성공: OK
→ 첫 조회

Key 있음
→ 저장하지 않음: nil
→ 이미 센 조회
```

- `NX`는 Key가 없을 때만 저장한다.
- `EX 86400`은 Key가 만들어진 뒤 86,400초 동안 유지한다.

여기서 TTL은 “얼마 동안 같은 조회로 볼 것인가”라는 업무 정책을 Key의 수명으로 표현한다.

다만 `EX 86400`은 첫 조회 시점부터 24시간을 의미한다. 달력상 하루에 한 번을 원한다면 날짜를 Key에 포함하고 다음 자정까지의 만료 시간을 계산하는 등 정책에 맞는 Key와 만료 시점을 설계해야 한다.

```text
첫 조회부터 24시간에 한 번
→ EX 86400과 가까운 정책

매일 00:00부터 23:59까지 한 번
→ 날짜가 바뀌는 경계를 반영해야 함
```

중복 Key가 만들어졌다면 Counter를 증가시킨다.

```redis
INCR views:post:100
```

Redis의 `INCR`는 해당 숫자 값을 하나의 명령으로 원자적으로 증가시킨다. 동시에 여러 요청이 들어와도 각 증가분이 하나의 Counter에 누적된다.

`SET NX`와 `INCR`은 각각 원자적으로 실행되지만, 두 명령 사이에는 다른 요청이 끼어들 수 있다. 조회 여부 확인과 증가를 하나의 업무 단위로 묶으려면 두 명령의 경계까지 설계해야 한다.

## 5. Redis 명령 사이에도 실패 구간이 있다

첫 조회를 처리하는 흐름은 두 단계다.

```text
1. SET NX로 중복 Key 생성
2. INCR로 Counter 증가
```

두 명령 사이에서 프로세스가 종료되면 어떻게 될까?

```text
SET NX
→ 성공

그런데

INCR 실행 전에 프로세스 종료
```

남은 상태는 다음과 같다.

```text
중복 Key
→ 존재
→ 다음 요청은 이미 본 것으로 판단

Counter
→ 증가하지 않음
```

조회 하나가 사라졌지만 다음 요청으로 자연스럽게 복구할 수도 없다. 각각의 Redis 명령이 원자적인 것과, 두 명령을 합친 업무 작업 전체가 원자적인 것은 다른 문제다.

```text
SET NX
→ 하나의 원자적 명령

INCR
→ 하나의 원자적 명령

SET NX 성공 후 INCR
→ 두 명령 사이에 실패 구간 존재
```

두 동작이 반드시 함께 실행돼야 한다면 하나의 Redis 작업으로 묶는 방법을 검토해야 한다. 조건에 따라 분기해야 하는 이 사례에는 Lua Script나 Redis Function을 사용할 수 있다.

```lua
local created = redis.call(
    'SET',
    KEYS[1],
    '1',
    'NX',
    'EX',
    ARGV[1]
)

if created then
    return redis.call('INCR', KEYS[2])
end

return 0
```

Redis는 Script 실행 중 다른 명령이 끼어들지 않게 처리한다. 따라서 중복 Key 생성에 성공한 경우에만 Counter를 증가시키는 조건과 두 변경을 하나의 실행 단위로 묶을 수 있다.

여기서 하나의 실행 단위란 Script가 실행되는 동안 다른 Client의 명령이 중간에 끼어들지 않는다는 뜻이다. 관계형 DB Transaction과 달리 실행 중 오류가 발생해도 앞선 변경은 자동으로 Rollback되지 않는다. `redis.call()`에서 Runtime Error가 발생하면 오류가 Client로 반환되고, `redis.pcall()`을 사용하면 Script 안에서 오류를 직접 처리할 수 있다. 따라서 Script는 쓰기 전에 Key Type과 입력값을 확인하고, 필요한 오류 처리 범위를 정해 두어야 한다.

`MULTI`와 `EXEC`으로 여러 명령을 연속 실행할 수도 있다. 다만 Redis Transaction은 관계형 DB Transaction처럼 실행 중 오류를 만나면 앞선 명령을 자동 Rollback하는 구조가 아니며, 앞 명령의 결과를 보고 조건부로 다음 명령을 실행하는 흐름은 Lua Script나 Function이 더 직접적이다.

Redis Cluster에서 Script가 여러 Key를 다룬다면 관련 Key가 같은 Hash Slot에 있어야 한다. 예제처럼 Key 이름에 같은 Hash Tag를 넣어 함께 배치하는 방법을 검토할 수 있다.

```text
viewed:post:{100}:member:15
views:post:{100}

{100}
→ 같은 Hash Tag
→ 같은 Hash Slot에 배치
```

여러 명령이 하나의 업무 단위를 이룬다면 **중간 실패 후 어떤 상태가 남는지 확인해야 한다.** Script 문법보다 이 실패 경계를 이해하는 것이 중요하다.

Redis에서 중복 판단과 증가를 안전하게 묶었다. 이제 DB에 매번 UPDATE하지 않고 Counter에 증가분을 모으려면, 그 값을 나중에 DB로 옮기는 새로운 작업이 필요하다.

## 6. Redis의 증가분을 나중에 DB에 반영한다

매 조회마다 DB를 UPDATE하는 대신 Redis에서 빠르게 증가시키고 일정 주기로 합계를 DB에 반영할 수 있다.

```text
조회 1,000번

기존
→ DB UPDATE 1,000번


Redis에 집계
→ Redis INCR 1,000번
→ 증가분을 모아 DB UPDATE 1번
```

이 예시는 개념만 단순하게 보여준다. 실제 DB UPDATE 횟수는 반영 주기와 Key 수, 요청 분포에 따라 달라진다.

**Redis에 조회수를 쌓아두고 일정 주기로 DB에 옮기는 구조를 여기서는 지연 반영이라고 하겠다.** Redis Counter가 DB를 완전히 대체하는 것이 아니라, DB에 쓸 증가분을 잠시 모은다.

```text
조회 요청
→ Redis INCR

일정 주기
→ 누적 증가분 확인
→ DB view_count에 한 번에 더함
```

DB 쓰기 횟수를 줄이는 대신 “나중에 반영해야 하는 데이터”라는 새로운 상태가 생긴다. Redis의 숫자는 DB에 아직 들어가지 않은 중요한 증가분이므로 임시 Cache처럼 다룰 수 없다.

다음 질문에 답해야 한다.

- DB 반영 직전에 Redis나 프로세스가 장애를 만나면 증가분 유실을 허용할 것인가?
- DB 반영 후 Redis를 정리하기 전에 실패하면 같은 증가분이 다시 반영되지 않는가?
- 사용자 화면에는 DB 값만, Redis 값만, 두 값을 합친 결과 중 무엇을 보여줄 것인가?
- Redis에 있는 값 중 어디까지가 아직 대기 중이고, 어디까지가 DB에 반영 중인가?
- 어디까지 DB에 반영됐는지 어떻게 기억할 것인가?

Redis를 썼다는 사실은 이 질문에 답해주지 않는다. 이제 정상적인 반영 흐름보다 먼저, 가장 단순한 구현이 어떻게 실패하는지 살펴보자.

## 7. 지연 반영은 복구 상태까지 설계해야 한다

Redis Counter에 37이 쌓였다고 해보자.

```text
views:post:100 = 37

1. Redis에서 37 읽기
2. DB에 +37 반영
3. Redis Key 삭제
```

Redis 조회, DB 변경과 Redis 삭제는 서로 다른 저장소에서 실행되므로 하나의 Transaction으로 묶이지 않는다.

### DB 반영 뒤 Redis 정리에 실패하면 중복 반영된다

```text
DB에 +37 반영 성공
↓
Redis Key 삭제 전에 프로세스 장애
↓
Redis에는 37이 그대로 남음
↓
다음 반영 작업이 다시 DB에 +37
```

DB에는 같은 증가분이 두 번 들어갈 수 있다.

### 처리 중 새 조회가 들어오면 증가분이 사라질 수 있다

```text
Redis에서 37 읽음
↓
새 조회 5개가 들어옴
↓
Redis Counter = 42
↓
반영 작업이 Key 전체 삭제
```

DB에는 37만 반영됐는데 새로 들어온 5까지 함께 삭제된다. 중복 반영을 피하려다 새로운 증가분을 잃을 수 있다.

### 증가분의 상태를 구분해야 한다

지연 반영에서는 **각 증가분이 현재 어느 상태인지 구분할 수 있어야 한다.** Counter 숫자와 함께 처리 상태를 관리해야 복구할 수 있다.

```text
대기 중
→ 아직 DB 반영 대상

처리 중
→ 이번 반영 작업이 DB에 적용하는 중

완료
→ DB 반영 성공
```

현재 새로 들어오는 조회와 이미 DB 반영을 시작한 조회를 같은 숫자 하나로 관리하면 어디까지 지우고 재시도해야 하는지 알기 어렵다. 그래서 다음 두 상태를 분리할 수 있다.

```text
새 요청을 받는 Counter
vs
이미 반영 작업에 들어간 Counter
```

한 가지 사고 방식은 다음과 같다.

```text
views:post:100 = 37

처리 시작
→ processing:views:post:100:batch-21 = 37
→ views:post:100은 다시 0부터 새 증가분 수집

DB에 +37 반영

성공
→ processing Key 삭제

실패
→ processing Key 유지
→ 나중에 재시도
```

대기 Counter에서 처리용 Key로 옮기는 과정도 중간 실패가 없도록 Redis Script나 적절한 원자적 명령 조합을 검토해야 한다. 처리 중 값을 애플리케이션 메모리에만 들고 있다가 프로세스가 종료되면 복구할 위치가 사라진다.

Processing Key는 특정 구현을 강제하려는 것이 아니다. Key 이름보다 다음 질문에 답할 수 있는 상태 관리가 중요하다.

- 어떤 증가분이 아직 대기 중인가?
- 어떤 증가분이 처리 중인가?
- 어떤 증가분이 완료됐는가?
- 실패하면 어느 상태부터 다시 처리할 것인가?

### 재시도할 때 같은 증가분을 두 번 넣지 않아야 한다

Batch 21의 증가분 37을 DB에 반영했다고 해보자.

```text
Batch 21의 +37
↓
DB 반영 성공
↓
성공 상태를 기록하기 전에 프로세스 장애
```

재시작한 애플리케이션은 이 증가분이 이미 DB에 들어갔는지 판단하기 어렵다.

```text
아직 미반영인가?
→ 다시 +37 필요

이미 반영됐는가?
→ 다시 +37하면 중복
```

같은 반영 묶음을 두 번 적용하지 않도록 `batch-21` 같은 Batch 식별자나 마지막 반영 지점을 DB에 기록하는 방법을 검토할 수 있다. Batch는 DB에 한 번에 반영할 증가분 묶음이다.

```text
DB Transaction

Batch 21 처리 기록 INSERT
+
post.view_count에 +37

둘 다 Commit
```

Batch 21의 처리 기록에 Unique Constraint를 두면 같은 Batch가 재시도돼도 중복 INSERT를 거부할 수 있다. 중복 Batch임을 확인한 재시도는 Counter를 다시 더하지 않는다.

같은 작업을 여러 번 요청해도 결과가 한 번 적용된 것처럼 유지되는 성질을 `Idempotency`, 즉 멱등성이라고 한다. **재시도할 때 이미 처리한 증가분인지 판단할 근거가 있어야 한다.** 용어보다 이 기준이 중요하다.

마지막 반영 지점을 저장하는 방식도 가능하다. 어느 쪽이든 정확히 한 번 반영하려면 Redis의 처리 상태와 DB의 반영 기록을 함께 관리해야 한다.

### 화면에 보여줄 숫자도 정해야 한다

DB에는 1,000이 있고 Redis 대기 Counter에 12가 있다면 사용자에게 무엇을 보여줄까?

```text
DB 값만 표시
→ 안정적이지만 최근 12는 아직 보이지 않음

DB + 대기 Counter 표시
→ 더 최신에 가깝지만 처리 중인 증가분을 빠뜨릴 수 있음

DB + 대기 + 처리 중 표시
→ DB 반영 직후 Processing Key 삭제 전에는 중복 합산할 수 있음
```

정답은 요구 정확도와 상태 전이 방식에 따라 달라진다. DB 반영이 끝난 시점과 Processing Key를 완료 처리하는 시점 사이에서 무엇을 합산할지까지 정해야 한다.

조회수나 좋아요 수처럼 몇 초의 지연이나 소량의 오차를 허용할 수 있는 지표라면 Redis 기반 절충이 합리적일 수 있다. 반면 결제 금액이나 재고처럼 누락과 중복이 업무적으로 허용되기 어려운 값에는 같은 방식을 그대로 적용하면 안 된다.

```text
조회수·좋아요 수·일부 통계

몇 초 지연 또는 소량 오차
→ 서비스 정책에 따라 허용 가능할 수 있음


결제 금액·재고

누락 또는 중복
→ 업무적으로 허용하기 어려움
```

**기술은 그 숫자가 틀렸을 때 어떤 문제가 발생하는지를 기준으로 선택해야 한다.** 숫자를 증가시키는 방법은 그다음 문제다.

## 실제 설계에서 확인할 순서

```text
조회수 기능이 필요함
↓
먼저 "조회 1회"의 의미 결정

누구 기준인가?
→ Account / Cookie / IP 등

얼마 동안인가?
→ 매 요청 / 24시간 / 달력 날짜별 / 전체 기간 등


증가 연산은 안전한가?
↓
현재 값을 읽어서 Java에서 +1 하는가?
→ 단순 Counter라면 DB 원자적 UPDATE 우선 검토


중복 기록은 어디에 둘까?
↓
DB 쓰기가 감당 가능한가?
→ DB Unique Constraint와 같은 Transaction

실제 병목이 확인됐는가?
→ Redis 중복 Key와 Counter 검토


Redis를 사용한다면
↓
SET NX와 INCR가 하나의 업무 단위인가?
→ 명령 사이 실패와 원자성 검토


DB에 바로 반영하지 않는다면
↓
증가분 유실 허용 범위는?
중복 반영을 어떻게 막을까?
어느 상태부터 재시도할까?
대기·처리 중·완료를 어떻게 구분할까?
```

이를 구현 단계로 다시 줄이면 다음과 같다.

```text
1단계

DB 원자적 UPDATE
+
Unique Constraint
+
같은 Transaction

↓ 실제 병목 없음

여기서 끝


↓ 실제 DB 쓰기 병목 확인


2단계

Redis 중복 Key
+
Redis Counter


↓ DB 지연 반영까지 필요


3단계

대기 / 처리 중 / 완료 상태
+
Retry
+
중복 반영 방지
+
복구 기준
```

실제 문제가 확인될 때 필요한 복잡성만 추가한다.

## 정리

- 조회수 증가분이 사라지는 동시성 문제와 같은 사용자의 반복 요청을 몇 번으로 셀지 정하는 업무 정책은 서로 다른 문제다.
- 단순 Counter는 값을 읽어 Java에서 계산하기보다 `view_count = view_count + 1` 형태의 원자적 UPDATE를 먼저 검토한다.
- 중복 조회는 사용자 식별 기준과 중복 제한 기간을 먼저 정한 뒤 DB 고유 제약 조건이나 Redis Key로 표현한다.
- DB의 원자적 UPDATE와 Unique Constraint만으로 필요한 처리량이 나온다면 그 구조가 더 좋은 선택일 수 있다.
- Redis `INCR` 하나는 원자적이지만 `SET NX → INCR`이라는 업무 흐름 전체에는 실패 구간이 남는다.
- Redis에 증가분을 모아 DB 쓰기를 줄이면 대기·처리 중·완료 상태, 재시도와 중복 반영 방지까지 설계해야 한다.

조회수는 **증가 연산의 정확성, 한 번의 조회를 정하는 기준, 쓰기 부하와 지연 반영 실패의 복구 위치를 서로 다른 문제로 나눠 설계한다.** 단순한 구조로 요구사항을 만족할 수 있다면 거기서 시작하고, 실제 부하와 정확도 요구에 따라 필요한 복잡성만 추가하는 편이 좋다.
